## 핵심 구현

### 1. 링 버퍼 기반 TCP 패킷 프레이밍

**문제**
TCP는 스트림 기반이라 단일 `recv()`에서 여러 패킷이 합쳐지거나, 하나의 패킷이 여러 번에 나뉘어 도착한다. 수신 데이터를 즉시 처리하면 메시지 경계를 잘못 판단한다.

교재의 에코 클라이언트는 **자신이 보낸 길이를 알고 있어서** 그 값으로 경계를 판단할 수 있었다. 브로드캐스트로 바꾸면 남이 보낸 메시지를 받으므로 그 전제가 성립하지 않는다.

**해결**
클라이언트당 고정 크기 링 버퍼(`PER_HANDLE_DATA`, 4096바이트)를 두고 수신 바이트를 누적한다. 4바이트 Big Endian 길이 prefix를 `Peek()`으로 먼저 읽은 뒤, 해당 길이만큼 데이터가 쌓이면 패킷을 추출하는 루프를 반복한다.

세 가지 상태를 구분해 처리한다.

- 누적량이 prefix(4바이트)보다 작음 → 대기
- prefix는 왔지만 본문이 부족함 → 대기
- prefix + 본문이 모두 도착 → 추출 후 루프 계속

**설계 판단**
처리한 데이터를 앞으로 당기는 복사 비용을 피하기 위해 선형 버퍼 대신 링 버퍼를 선택했다. 읽기·쓰기 위치만 이동하므로 삽입과 추출이 O(1)이다. 한 칸을 비워 두어 가득 참과 비어 있음을 구분한다.

길이 prefix가 `MAX_PACKET`(512바이트)을 초과하면 프로토콜을 따르지 않는 데이터로 보고 즉시 연결을 끊는다. 이 검증이 없으면 잘못된 헤더 하나로 해당 세션이 영구히 대기 상태에 빠진다.

**결과**
분할·병합 수신 상황 모두에서 메시지 경계가 복원됨을 확인했다. 검증 방법은 아래 [검증](#검증) 참조.

### 2. IOCP + 워커 스레드풀 구조

**문제**
블로킹 `recv()` 기반 모델은 클라이언트 하나당 스레드 하나가 필요하다. 접속자가 늘면 스레드 수가 선형으로 증가한다.

**해결**
Windows IOCP에 비동기 `WSARecv()`를 등록하고, CPU 코어 수만큼만 워커 스레드를 생성한다(`_beginthreadex`). 각 스레드는 `GetQueuedCompletionStatus()`에서 대기하다 완료 통지가 올 때만 깨어난다.

소켓을 IOCP에 등록할 때 `PER_HANDLE_DATA` 포인터를 completion key로 전달해, 완료 시점에 별도 조회 없이 해당 클라이언트의 링 버퍼에 접근한다.

**설계 판단**
교재는 완료 루틴(Completion Routine) 방식도 함께 다루지만 IOCP를 선택했다. 완료 루틴은 IO를 요청한 스레드가 alertable wait 상태에 있어야 콜백이 실행되므로 `SleepEx`로 계속 양보해야 하고, 처리가 그 스레드에 묶인다. IOCP는 워커 풀로 완료 처리를 분산할 수 있다.

스레드 수를 코어 수로 고정해 튜닝 필요성을 없앴다.

**결과**
구조상 스레드 수가 접속자 수와 무관하게 코어 수로 고정된다. 다만 동시 접속 규모에 따른 성능은 측정하지 않았다.

### 3. 뮤텍스 보유 시간 최소화 브로드캐스트

**문제**
브로드캐스트는 소켓 배열을 순회하며 `WSASend()`를 호출한다. 그동안 다른 워커 스레드가 접속 종료를 처리하며 같은 배열을 시프트할 수 있다. 순회 중 배열이 변경되면 이미 닫힌 소켓으로 송신하거나 범위 밖을 읽는다.

에코 서버는 자신에게만 응답하므로 배열을 순회할 일이 없어 이 문제가 없었다. 브로드캐스트로 확장하면서 생긴 문제다.

**해결**
락을 잡아 소켓 배열을 로컬 스냅샷으로 복사한 뒤 즉시 해제한다. 이후 스냅샷을 기준으로 `WSASend()`를 순회한다. 접속 추가와 종료 처리에도 같은 뮤텍스를 적용했다.

각 전송 대상마다 `PER_IO_DATA`를 별도 할당한다. 진행 중인 비동기 작업은 각자의 `OVERLAPPED`를 가져야 하며, 하나를 공유하면 완료 통지의 동작이 정의되지 않는다. 버퍼도 함께 분리해 송신 완료 전에 덮어써지는 것을 막는다.

**설계 판단**
락을 잡은 채로 `WSASend()`를 돌리면 보유 시간이 접속자 수에 비례해 길어지고, 그동안 accept와 종료 처리가 모두 대기한다. 목록 복사만 락 안에서 수행해 보유 시간을 접속자 수와 무관하게 고정했다.

스냅샷 시점과 송신 시점 사이에 대상이 끊길 수 있다. 이 경우 `WSASend()`가 실패하므로 반환값을 확인해 컨텍스트를 즉시 해제한다.

**결과**
브로드캐스트 순회 중 배열이 변경되는 경합 구간을 제거했다.

## 검증

경계 조건을 의도적으로 만들어 확인했다.

| 케이스        | 방법                              | 관찰 결과                                      |
| ---------- | ------------------------------- | ------------------------------------------ |
| **패킷 병합**  | 두 패킷(각 13바이트)을 하나의 버퍼로 합쳐 1회 전송 | 34바이트를 1회 수신한 뒤 13바이트짜리 2개로 분리해 각각 브로드캐스트  |
| **패킷 분할**  | 길이 prefix와 본문을 나누어 전송           | prefix 수신 후 본문이 도착할 때까지 대기했다가 조립           |
| **잘못된 헤더** | 프리픽스 없이 원시 문자열 전송               | 본문이 길이 필드로 해석되어 `MAX_PACKET` 검증에 걸리고 연결 종료 |

세 케이스가 각각 다른 코드 경로를 검증한다. 병합은 추출 반복문, 분할은 대기 조건, 잘못된 헤더는 길이 검증이다.

## 알려진 한계

- **단방향 프레이밍** — 클라이언트에서 서버로 보낼 때만 길이 prefix를 사용한다. 서버가 브로드캐스트할 때는 본문만 전송하며, 클라이언트 수신 측 프레이밍은 구현하지 않았다. 같은 이유로 서버에서 클라이언트 방향에도 경계 문제가 남아 있으며, 양방향 적용이 다음 작업이다.
- **세션 수명 관리** — 종료 시 `PER_HANDLE_DATA`의 해제를 보류했다. 진행 중인 비동기 송신이 해당 객체를 참조할 수 있어 즉시 해제하면 해제된 메모리에 접근할 위험이 있다. 참조 카운팅 기반의 세션 관리가 필요하다.
- **부하 테스트 미실시** — 경계 조건만 확인했고 동시 접속 규모나 처리량은 측정하지 않았다.
- **브로드캐스트 비용** — 메시지 하나당 접속자 수만큼 송신이 발생한다. 규모가 커지면 채널 분리나 배치 전송이 필요하다.

## 빌드 및 실행

```
언어 / 빌드 : C++ · Visual Studio 2022 (v143 툴셋)
플랫폼      : Windows x64
의존성      : Winsock2 (ws2_32.lib) — 프로젝트에 이미 설정됨
수신 포트   : 9190
```

1. 레포를 클론합니다.
2. `IOCPUnityServer/IOCPUnityServer.sln`을 Visual Studio 2022에서 엽니다.
3. 구성 `Debug | x64` 선택 후 빌드합니다.
4. `x64/Debug/IOCPUnityServer.exe`를 실행하면 포트 9190에서 수신 대기합니다.
5. [Unity 클라이언트](https://github.com/khs081215/ChattingClient)를 함께 실행해 연결합니다.

## 프로토콜

```
[4바이트 길이(Big Endian)][본문(UTF-8)]
```

- 길이 필드는 본문의 바이트 수이며 헤더는 포함하지 않는다.
- 최대 본문 크기는 512바이트(`MAX_PACKET`)이며 초과 시 연결을 끊는다.
- 현재 클라이언트에서 서버로 보내는 방향에만 적용된다.
